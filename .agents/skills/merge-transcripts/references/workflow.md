# 発話録統合作業の手順

## 1. 依頼固有の条件を確定する

テキストを変換する前に、次の依頼固有事項を記録する。

- 入力が、toittaからダウンロードしたCSVと、会議ツールが生成したVTTまたはMarkdownの組み合わせか。
- 各ソースのタイムスタンプ、収録範囲、話者情報の由来に、既定の想定と異なる点があるか。
- 会議テーマ、必須の話者ラベル、匿名化規則、固有用語は何か。
- すべてのソースが同じ時間範囲を収録しているか。
- [Skillの既定の入力ソースの役割](../SKILL.md#既定の入力ソースの役割)に対する明示的な例外が、現在の依頼にあるか。
- [Skillの既定の出力条件](../SKILL.md#既定の出力条件)に対する明示的な例外が、現在の依頼にあるか。

既定の入力ソースの役割と出力条件はそのまま適用し、それ以外の答えを過去のインタビューから推測してはならない。

## 2. 入力ソースを設定する

toittaのCSVを原則として `skeleton_source` とし、チャンク粒度と文脈を踏まえた表記の基準にする。会議ツールが生成した、タイムスタンプ付きの細粒度なVTTまたはMarkdownを原則として `boundary_source` とし、話者境界の基準にする。追加のタイムスタンプ付きソースやタイムスタンプなしソースは、文脈上の根拠として指定できる。現行CLIでは、骨格となるすべてのセグメントに開始タイムスタンプが必要である。

Markdownに対応付け可能なタイムスタンプがない場合は `boundary_source` に指定せず、時系列の話者根拠として精査した結果をセグメント番号付きの `overrides` に記録する。

入力元の話者IDは、現在の出力条件で許可された名前だけに対応付ける。ユーザー本人の元の氏名、ユーザー名、話者IDは、指定された最終話者ラベルに対応付ける。また、出力へ残してはならない元表記を正規表現としてエスケープし、`forbidden_patterns` にも設定する。同じ表記が別人を指す可能性がある本文箇所は、文脈を確認してセグメント番号付きの `overrides` で修正する。フォールバック時の話者は別に設定する。CSVの話者ID、`TRUE/FALSE`、同様の分類フィールドは、話者境界の根拠として使用しない。

## 3. 対応付けの前に入力を確認する

次を実行する。

```bash
transcript-reconcile inspect --config /path/to/session.json
```

件数、最初と最後のタイムスタンプ、想定外の話者、空のソース、収録範囲の部分的な欠落を確認する。見た目が整ったソースでも、話者境界が誤っていることはある。

## 4. 暫定稿とレビューレポートを生成する

次を実行する。

```bash
transcript-reconcile reconcile \
  --config /path/to/session.json \
  --output /path/to/draft.md \
  --review /path/to/review.jsonl
```

ツールは、骨格となる各行の区間を、その行のタイムスタンプから次の行のタイムスタンプまでとして扱う。重複する境界キューを、正規化後に共通するテキストと時間の重なりに基づいて採点する。複数の話者を含む行を自動では分割しない。重なりが弱い第2の話者は診断用の根拠として保持するが、それだけでレビュー対象にはしない。これにより、読みやすいソースには存在しないフィラーでレビュー対象が埋め尽くされるのを防ぐ。

`needs_review` が付いたレコードを優先するが、信頼度が高いと判定されたレコードも抜き取り確認する。各候補について、骨格のテキスト、時系列順の境界キュー、話者スコア、追加ソースとの一致を比較する。非常に短い相づちは、発話時刻から話者を明確に判断できる場合でも、共通テキストによる根拠が弱いことがある。

## 5. 判断結果を再現可能な形で記録する

確定した分割や会議固有の表記修正は、すべてセグメント番号を指定した `overrides`（個別上書き）として追加する。表示上のタイムスタンプが重複しても、セグメント番号は変わらない。同じ修正をすべての出現箇所に適用しても安全な場合に限り、`replacements`（一括置換）を使用する。

設定を編集したら、コマンドを再実行する。重要な最終修正を生成済みMarkdownだけに加えてはならない。再生成時に失われるためである。

## 6. 文脈に基づいて表記を精査する

提供された2つ、またはすべてのソースを比較する。ソースに裏づけられ、前後の会話にも合う表記を優先する。固有名詞、サービス名、製品名、専門用語に不明または曖昧な点がある場合は、必要に応じてネット検索し、公式情報を優先して表記を確認する。確実でない内容を作り上げるのではなく、未解決の不確実性を記録する。

## 7. 監査して納品する

次を実行する。

```bash
transcript-reconcile audit \
  --config /path/to/session.json \
  --input /path/to/final.md
```

リンク先のレビューチェックリストをすべて完了する。収録されていない時間範囲、未解決の表記、音声を確認していないことを報告する。現在の依頼に既定条件への明示的な例外がある場合は、実際に行った確認範囲を正確に報告する。
